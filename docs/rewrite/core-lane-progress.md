## Design: why no NativeFinalizer, and the guardian isolate
- **mpv aborts** if a handle is destroyed while a render context is alive. Verified in mpv 0.41 `player/client.c`: `mp_destroy_client` → (last strong client) `mp_destroy` → `mp_clients_destroy`, which prints "Broken API use: mpv_render_context_free() not called." and calls `abort()`. So the handle is destroyed only after the release callbacks, and never blindly while a desktop VideoController may hold one.
- **A NativeFinalizer can't be the safety net from Dart.** Its callback can only be a libmpv function. The VM runs it in VM state under `NoSafepointScope` (`Isolate::RunAndCleanupFinalizersOnShutdown`, `NativeFinalizer::RunCallback`). `mpv_terminate_destroy` blocks on mpv threads, and those threads call the wakeup `NativeCallable`, which allocates on the Dart heap (`FfiAsyncCallbackSend`). A pending safepoint then deadlocks the process. The finalizer also can't clear the wakeup callback first (that takes 3 arguments). Doing it safely needs the C bridge (Predidit's design).
- **The Dart-only replacement: a guardian isolate per owner isolate.**
  - It owns the wakeup `NativeCallable.listener` and forwards each wakeup to the owner. When the owner dies, the callable stays valid, so there's no "Callback invoked after it has been deleted" (#1348).
  - It gets `Isolate.addOnExitListener` of the owner. On exit, it clears the wakeup of each handle still alive and destroys it, or only sends `quit` if the handle may have a render context (marked when a VideoController attaches on desktop).
  - dispose hands a handle over with one `destroy` message, so a handle is destroyed exactly once whenever the owner dies. The guardian runs the destroy in `Isolate.run`.
  - Cost: one extra port hop per wakeup, not per event.
- **The isolate-based delivery** (debug main isolate, execmem-restricted) is unchanged in design. dispose waits for its helper to leave `mpv_wait_event`, then destroys in `Isolate.run`. Hot restart still goes through NativeReferenceHolder (`quit`, no destroy).

## No libmpv call waits for mpv's core on the UI thread (2026-11-08, `core-async`)
Starsync on Linux (X11, NVIDIA): event-loop stalls of 18.7, 29.5 and 49.6 s, then `[ao/openal] could not open device`. mpv's core thread was stuck opening the audio device, and a synchronous libmpv call (`mpv_get_property*`, `mpv_set_property*`, `mpv_command`) waits for the core (`run_locked` / `lock_core` in `client.c`). Reproduced headless: ao=pcm on a FIFO without a reader blocks the core in `fopen` (`core-blocked-does-not-block-event-loop`: 2.5 s stall before, 10 ms after).
- Now asynchronous: `getProperty` (`mpv_get_property_async`, `MPV_EVENT_GET_PROPERTY_REPLY`), `setPropertySync` (sent without waiting; a hook in progress lets mpv continue only once it's applied, so `onPreloadedHooks` keep their order guarantee), the `on_load`/`on_unload` work (path, playlist-pos, http-header-fields, start/end), the hot-restart `quit`, media_kit_video's `queryDecoders` (`decoder-list` read as JSON), and the Linux VideoOutput's `video-sync`/`video-timing-offset` (moved from the platform thread to `NativeVideoController.create`). `_hasOption` is gone: `osc` is set always.
- Still synchronous, and why they can't wait long: `mpv_hook_continue` (the core sits in `process_hooks` → `mp_idle`, which answers lock requests, until this very hook continues), `mpv_create`/`mpv_set_option_string`/`mpv_initialize` (a fresh core, before anything is observed). `mpv_hook_add` runs in a worker isolate: observing `audio-device-list` makes the core open the audio hotplug, which can hang (CI: PipeWire without a server; a synchronous `mpv_hook_add` right after froze the test isolate, and its process at exit). With `NativePlayer.test`, `audio-device`/`audio-device-list` aren't observed: on CI, libpipewire's failure path hung the core in `pw_thread_loop_stop` at destroy (gdb on the runner), and the test process at exit. `PlayerConfiguration.async: false` keeps the synchronous API on request. `screenshot`/`setShuffle` read in a `compute` isolate, not on the UI isolate. No core lock: `mpv_wait_event`, `mpv_observe_property`, `mpv_unobserve_property`, `mpv_request_event`, `mpv_request_log_messages`, `mpv_set_wakeup_callback`.
- Native code that still waits for the core: Linux `mpv_render_context_free` on the platform thread at VideoController dispose (`kill_video_async`, then waits for the VO), and the Linux texture's `video-out-params` read on the raster thread when the output has no fixed size.
- Log: a failed request's reply was logged twice, the second time as `event:mpv_event_id.MPV_EVENT_SET_PROPERTY_REPLY Pointer: address=0x0` (`log-failed-set-once`). "property not found" for options that only Lua builds have (`ytdl`, `osc`, ...; freeKC on Windows has no Lua) is logged at `debug` level. Starsync sets `ytdl=no` itself (`_pinCache`).
- `on_unload` reset `http-header-fields` with an `MPV_FORMAT_NONE` node, which mpv refuses: the error was ignored by the synchronous call. Now an empty string.
- Android: dispose sets `vid=no`, `vo=null`, `wid=0` before the release callbacks, so mpv lets go of the Surface before it's released.
- #1420: `MPV_FORMAT_FLAG` is a C int. `_setPropertyFlag` passed a 1-byte buffer (over-read on every `pause`); flag changes were read as their first byte.
- Not done: Windows `gpu-hwdec-interop`. mpv's render API loads every GL interop when it's `auto`, hence `dxva2-egl` "Failed to create EGL surface" on ANGLE/D3D11. `d3d11-egl` before `mpv_render_context_create` should stop it, but CI has no GPU and its Windows tests use `vo=null`: nothing there can show d3d11va still works.

## Left
- Owner killed during an in-flight `screenshot`/`setShuffle` `compute`: the guardian may destroy the handle under it. The fix is the async `screenshot-raw` and async `playlist` get from the FFI item below.
- Release-mode app exit with a desktop VideoController: if the engine kills the isolate group before the guardian handles the owner's exit, the callable is deleted with the wakeup still set. This was pre-existing, and the window is now smaller. Only the C bridge closes it.
- Windows `VideoOutputManager.Create`/`Dispose` run on detached threads that race for one mutex. A `Dispose` that wins over a pending `Create` leaves an output (and a render context) for a handle that's being destroyed. Dart covers it only by waiting for the VideoController's init before the destroy. The native fix is one ordered queue (Windows lane).
- Not done from the old plan: P1-C0 split, `reply_userdata` dispatch for internal observers, UI-rate position, FFI fixes (flag width, argv size, async screenshot/playlist), CA bundle, `malloc_trim` proposal.
